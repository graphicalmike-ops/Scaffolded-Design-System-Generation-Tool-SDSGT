## Subject 2 — Layer 2: actually vendoring components

This splits into two genuinely different problems — confirmed by checking how each library actually distributes its components, not assumed:

### Pattern A — npm-dependency libraries (React Native Paper, Vuetify) — **done, 2026-09-11**

No vendoring at all. "Installing" means: add the npm package, wrap the app in the library's theme provider, pass in the `theme.ts` this pipeline already generates. No curated component list to choose (the whole library ships as one package), no customized-file-marking problem (nothing gets copied into the user's repo to diverge from upstream).

**Verified, not assumed (2026-09-11):** neither library has an init command that can wire a provider into an *existing* project. React Native Paper has no scaffolding/init CLI at all (`oss.callstack.com/react-native-paper` — always a manual `PaperProvider` wrap). Vuetify's `npm create vuetify`/`create-vuetify` only scaffolds a brand-new project (confirmed against Vuetify's own `packages/docs/.../installation.md`, master branch) — no mode targets an existing one. So the answer to "run something vs. emit a snippet" is settled: emit a snippet, for both.

**Built:** `generate --rn-paper` and `generate --vuetify` each now also write a `SETUP.md` next to `theme.ts` — real npm install command(s), RN Paper's optional `babel.config.js` bundle-size plugin, and a ready-to-copy provider-wiring snippet (`PaperProvider`/`createVuetify()`) that imports `theme.ts`'s *actual* export names (`LightTheme`/`DarkTheme` or `lightTheme`/`darkTheme`), branched on whichever of light/dark really exist — not a hardcoded both-modes assumption. See `contracts-and-seeds.md`, "React Native Paper theming"/"Vuetify theming," for the written-up decision. QA coverage added in `scripts/qa-matrix/checks.ts` (`checkRnPaper`/`checkVuetify`): asserts `SETUP.md` exists and that its imports/`defaultTheme` match what `theme.ts` actually exports for that seed's light/dark mode — full matrix run clean (35/35 cases, 5111 checks, 0 anomalies). No real Layer 3 infrastructure was needed for this, confirming the original guess above.

### Pattern B — copy-paste libraries (shadcn/ui done 2026-09-12, RNR done 2026-09-14)

Real vendoring. Installing means running the library's own CLI against a **real, already-initialized project** — `shadcn add` specifically needs `components.json` already present, which only exists after `shadcn init` has run inside a real Next.js+Tailwind project. This is what actually coupled Layer 2's hard half to Layer 3: there was no way to vendor a real shadcn component without a real scaffolded project to vendor it into — which is why this waited for the Next.js scaffold slice above.

**shadcn/ui built** (`cli/src/scaffold/nextjs.ts`, `scaffold --framework nextjs --shadcn`) — the three open decisions below are now resolved, each confirmed against a real end-to-end run (real build succeeded with 61 real vendored components + this pipeline's own brand colors/fonts applied):

- **Curated/trimmed component list — decided: everything.** `shadcn add --all -y` vendors the entire current registry (61 components at time of building, confirmed via a real run) rather than a curated subset. Chosen over a curated list specifically so the user never has to come back and run `shadcn add <name>` by hand for something this pipeline could have already vendored — matches `pipeline-plan.md`, "Who this is for, and the bar for 'done.'" RNR needs this same decision made independently when its turn comes (its own catalog, not identical to shadcn's).
- **Customized-file marking (the ACIM lesson) — decided: a manifest with content hashes.** `sdsgt-vendored-components.json`, written at the project root, records each vendored file's path + a SHA-256 hash of its original content (`{ "shadcn": { "button": { "path": "...", "hash": "..." }, ... } }`). A future re-vendor step (not yet built) or an AI agent can compare a file's current hash against the manifest: unchanged means safe to re-vendor, changed means customized — leave it alone. `generate/project-docs.ts`'s `AGENTS.md` rule for shadcn now names this file explicitly, closing the gap the rule used to only gesture at. Nothing reads the manifest back yet — writing it is this session's scope; the re-vendor step that would consume it is a separate, not-yet-built piece.
- **Theme wiring order — decided: append, don't suppress or replace.** Real testing (`shadcn init -d -y`, current CLI v4.21.0) confirmed there's no flag to suppress its default theme generation — it always writes a real, structurally-necessary `globals.css` (imports, dark-mode custom-variant, the generic `@theme inline` mapping that real vendored components' Tailwind utility classes depend on) with its own default OKLCH values, and even vendors one Button component by default. Rather than parsing and replacing that structure, this pipeline's own `generate --shadcn` output (already using shadcn's exact CSS variable names, e.g. `--primary`, `--card`) gets **appended** to the end of the file. CSS's own cascade — a later declaration of the same custom property under the same selector wins — makes this correct without ever touching shadcn's generated structure, confirmed by inspecting the real compiled output through a real build: two "dead" earlier `:root`/`.dark` blocks (shadcn's own defaults, superseded) followed by one live one (this pipeline's real values). Font roles (`--font-sans`/`--font-heading`, shadcn's only two) get this project's secondary/primary fonts respectively, same append strategy.

Also confirmed and worth remembering: `shadcn add --all` re-running against `init`'s already-vendored Button correctly detected an identical file and skipped it rather than erroring or duplicating — no extra handling needed for that overlap.

**RNR — blocked, real reasons, 2026-09-12 (decided: don't build around it, don't script keystrokes).** Investigated for real (ran the actual CLI, not docs/training-data assumptions) before concluding this — the situation turned out meaningfully different from shadcn's, not just "the same pattern for a second library":

- **RNR has its own separate CLI** (`@react-native-reusables/cli`; not a shadcn registry despite the shared design philosophy). **Correction, 2026-09-14:** the `1.0.0` real-current-version claim recorded here on 2026-09-12 was itself wrong — real npm version history tops out at `0.7.1` (confirmed via `npm view @react-native-reusables/cli versions`). The confusion is explainable, not just an error: the CLI's own `--help`/`--version` output prints `@react-native-reusables/cli 1.0.0` as a hardcoded self-reported string that doesn't match its published `package.json` version at all — a real, verified discrepancy between what the tool says about itself and what npm actually has, worth remembering if this ever needs re-checking again. `add` looks fully automatable on paper: `-y`/`--yes`, `-a`/`--all`, `--styling-library nativewind|uniwind`, mirroring shadcn's `add` closely.
- **`init`, however, is a fully interactive wizard with no flag to skip any of it** — confirmed by actually running it against both an empty directory and an already-scaffolded Expo project: asks for a project name (no positional argument or flag found), asks you to pick a template via an arrow-key menu (Minimal NativeWind / Minimal Uniwind / Clerk auth NativeWind), asks "install dependencies?" (Y/n), then asks which package manager — **defaults to `bun`, not npm** — and when the default was accepted on this machine (no `bun` installed), the install step failed outright. None of `init`'s documented flags (`-c`/`--cwd`, `-t`/`--template`) cover any of this.
- **A real chicken-and-egg problem shadcn's slice never had:** `add` needs NativeWind already configured in the target project, which normally comes from `init`. Unlike shadcn (which had the already-built Next.js scaffold to install into), **this pipeline has no Expo/React Native scaffold at all yet** — so even setting `init` aside, there's no existing "Layer 3 for React Native" to hand `add` a project.

**Decided: stop here, don't script around it.** The alternative — piping the exact expected keystroke sequence (typed project name, arrow-key menu selections, "y") into `init`'s stdin — would work today but is fragile by construction: it isn't reading a documented contract, it's mimicking a human typing, and breaks silently the moment RNR reorders or rewords a prompt. That's a real conflict with this project's own "determinism is a project-wide goal" principle (`pipeline-plan.md`, "Three layers"), in a way every other scaffolding integration in this pipeline (`create-next-app`, `shadcn`) never had to trade off, since both of those ship real non-interactive flags.

**Re-verified 2026-09-14, still blocked at the time — the Expo scaffold now exists (Subject 5, below), but the CLI blocker was real and independent.** With a real `create-expo-app`-scaffolded project now on disk (something that didn't exist on 2026-09-12), `@react-native-reusables/cli@latest init -t default` was run again, non-interactively, stdin closed. It hangs — confirmed via `--log-level trace` that it's genuinely alive and waiting, and via a bounded background run that it's sitting on a live interactive menu: `"A project already exists in this directory. How would you like to proceed?"` with three arrow-key options. No flag bypasses this specific prompt. So the chicken-and-egg half of the original blocker (no Expo scaffold to install into) was resolved, but `init`'s own interactivity was not — **that conclusion about `init` specifically was correct and still stands.**

**REVERSED the same day, once `add` was tested standalone instead of via `init` — real vendoring works.** The user asked, after Kotlin/SwiftUI both got resolved as guides, whether the same treatment could apply to RNR. It can't (RNR's whole point is vendoring real component *source*, not a project-creation gap a guide can solve) — but that question prompted re-testing whether `add` (which already had real non-interactive flags: `-a`/`--all`, `--styling-library`) could run standalone against a project that never went through `init` at all, something flagged as "not yet tested" back on 2026-09-12 and still true as of the morning's Subject 5 re-check. It can. Run against this pipeline's own `scaffold --framework react-native` output:
- `add` correctly auto-detected NativeWind as the styling library by inspecting the real project — no `init`-derived state needed for that part at all.
- It then asked exactly two things, both real, satisfiable preconditions: (1) a plain y/n prompt — "Missing components.json — write one?" — which never fires if the file already exists (real schema fetched from RNR's own template repo, not guessed); (2) an arrow-key prompt — "Git repository is dirty — continue anyway?" (confirmed via a real bounded test that plain piped text does NOT satisfy it, same raw-keypress class as `init`'s own blocked menu) — which never fires if the working tree is actually clean (a real `git add -A && git commit`, since `create-expo-app` already initializes a real git repo).
- With both satisfied, `add -a --styling-library nativewind` completed for real: exit 0, 32 real component files, real `@rn-primitives/*` dependencies installed. One transient connect-timeout to `reactnativereusables.com` was hit once during testing and resolved on retry — same class of flakiness as create-vuetify's own template download (Subject 4), unrelated to the interactivity question.
- **Two more real gaps found by then typechecking the real output** (same discipline that caught shadcn-vue's own `@unovis` gap): `add --all` never vendors `lib/utils.ts` (the `cn()` helper almost every component imports — normally `init`'s job) — fixed by writing it directly, real content fetched from the same template repo. And `add --all` doesn't install every real dependency its own vendored files import — `react-native-screens`, `lucide-react-native`, `class-variance-authority`, `clsx`, `tailwind-merge` were all missing — fixed with explicit follow-up installs. A real `tsc --noEmit` and a real `expo export --platform web` both pass clean against the final output.

**Built as `--rnr` on `scaffold --framework react-native`** (`cli/src/scaffold/react-native.ts`), same customization-guard manifest treatment (`sdsgt-vendored-components.json`) as shadcn/shadcn-vue. See `contracts-and-seeds.md`, "React Native (Expo) scaffold (Layer 3)," for the full write-up. The lesson worth keeping: the original "don't script keystrokes" decision was correct and still applies to `init` — what changed the outcome was finding the tool has a *second*, less-interactive entry point (`add`) that doesn't need the blocked one at all, not reversing the decision itself.

## Subject 3 — Layer 3: project scaffolding

**Next.js + Tailwind slice built, 2026-09-12.** `cli/src/scaffold/nextjs.ts` (`node src/cli.ts scaffold --framework nextjs`) drives `create-next-app` non-interactively (verified: a full explicit flag set + `--yes` runs with zero prompts even with stdin closed), then layers this pipeline's already-generated Tailwind theme on top — colors, fonts, and agent-rules files all wired in before the user ever opens the project. Concretely, per run:
- Runs `create-next-app` with a locked flag set (TS, Tailwind, ESLint, App Router, `src/` dir, npm, git, `--no-agents-md` to suppress Next's own generic `AGENTS.md`/`CLAUDE.md` in favor of SDSGT's own).
- Copies in `theme.css`/`theme-light.css`/`theme-dark.css` from the matching `generate --tailwind --framework nextjs` run, and rewrites `globals.css` to import them plus set `body`'s background/text/font from the semantic tokens.
- Real fonts: deliberately does **not** use `next/font/google` (that API needs a static import matching Google's own current export identifier for the family — spaces to underscores — which risks drifting from whatever the user actually typed, since Google has renamed families before, e.g. "Source Sans Pro" → "Source Sans 3"). Instead reuses the exact same already-fetched `.woff2` files `promote --fonts-dir` already consumes (`shared/font-slug.ts`) and writes a plain hand-authored `@font-face` block using the literal family name already baked into every semantic typography token — no identifier-guessing, verified end-to-end with real fetched font files (build succeeded, font file served correctly at runtime).
- Strips Next's own placeholder homepage/Geist-font wiring, writes a minimal real page proving the tokens are live, and its own `README.md`/`AGENTS.md`/`foundations-rules.md`/`design.md` (copied from the `generate` run).
- Scope deliberately narrow, matching "the smallest possible Layer 3 slice" below: Next.js + Tailwind only. Bootstrap/MUI Next.js targets, and every other framework (Vue.js, React Native/Expo, Kotlin, SwiftUI), still have no scaffold builder.

**A real bug found and fixed in the process (2026-09-12):** the first real Next.js build of this pipeline's Tailwind output exposed that `generate/tailwind.ts`'s dark-mode file nested `@theme { ... }` inside `[data-theme="dark"] { ... }` — Tailwind v4 hoists any `@theme` block straight to the root regardless of what selector it's nested in, so dark values were silently overwriting light ones globally, all the time, not just under that selector. The QA matrix's existing checks never caught this because they only verified the generated file's raw text (does the selector string appear, are braces balanced), never what a real Tailwind compiler actually does with it. Fixed by using plain (non-`@theme`) custom properties under the selector instead, which behave the way an ordinary CSS custom property is expected to. A new check, `checkTailwindRealBuild` (`scripts/qa-matrix/checks.ts`), now actually compiles the generated CSS through the real `@tailwindcss/postcss` plugin and inspects the output — added `tailwindcss`/`@tailwindcss/postcss`/`postcss` as `cli/` devDependencies for this. Verified the check has real teeth by reintroducing the bug and confirming it fails with a clear message, then confirming it passes again once reverted. Full matrix: 35/35 cases, 5173 checks, 0 anomalies.

**Framework order, settled:** Next.js went first, per the recommendation below — Vue.js, React Native/Expo, Kotlin/Android Gradle, and Xcode/iOS remain unstarted. Given Subject 2's coupling, Next.js also sets up shadcn/ui as the natural next real end-to-end proof (Layer 1 tokens → Layer 2 theme → Layer 2 real components → Layer 3 scaffold, all the way through, for one pairing) — that's Pattern B, still open.

## Subject 4 — Layer 3: Vue.js scaffolding (both design-language paths)

**Built 2026-09-14.** The user confirmed up front that both Vue paths should be built in the same session, not staged — Vue + Tailwind (mirroring the Next.js slice) and Vue + Vuetify/Material Design (a genuinely separate pipeline: different official CLI, different theme source, no Tailwind involved at all). See `contracts-and-seeds.md`, "Vue.js scaffold (Layer 3)," for the full written-up contract — this section is the narrower "what broke and how it got fixed" record.

**None of the following were guessable from the Next.js precedent** — each is a real thing found by actually running the tools, not assumed from how `create-next-app`/shadcn/ui behaved:

- **create-vue has no `--tailwind` flag and does not auto-install its own dependencies** (`create-next-app` does both). This pipeline installs `tailwindcss`/`@tailwindcss/vite` itself in the same `npm install` call that covers create-vue's own base deps.
- **A real, current version drift**: create-vue's own `--eslint` template locks an `oxlint` devDependency version that has already drifted ahead of `eslint-plugin-oxlint`'s peer range — confirmed by hitting a real `ERESOLVE` against current npm registry state (not a local-machine fluke). Fixed with a project `.npmrc` (`legacy-peer-deps=true`), left in the generated project permanently (not just used transiently for this scaffold step) since the same drift would break the end user's own future `npm install`s too.
- **An absolute `--out` path silently breaks both create-vue's AND create-vuetify's non-interactive behavior**, in two different failure shapes — create-vue drops into a live interactive prompt (printed "Package name:" and created nothing, confirmed by checking the target path was empty afterward); create-vuetify instead silently creates the project under the *calling process's own cwd* instead of the intended path (confirmed by finding a real, unwanted project directory inside this repo's own `cli/` folder after a run — cleaned up, never committed). Both fixed the same way: run from the target's parent directory, pass just the bare basename.
- **shadcn-vue's installation checker needs `@import "tailwindcss"` already present, and reads the import-alias from the ROOT `tsconfig.json`** — create-vue's split-tsconfig template only sets the alias in `tsconfig.app.json`, and a fresh create-vue project's default `main.css` has no Tailwind import at all yet (unlike Next.js, where `create-next-app --tailwind` already established both before shadcn's own `init` ever runs). Fixed by seeding a one-line `@import "tailwindcss";` into `main.css` and writing the alias into the root `tsconfig.json` before calling `shadcn-vue init`.
- **`shadcn-vue add --all` has a real gap**: it vendors the `chart` component's source but never installs its registry-declared runtime dependency (`@unovis/vue` + `@unovis/ts`) — confirmed by a real `vue-tsc` typecheck failure that only cleared once these were installed by hand. Fixed with an explicit follow-up install.
- **shadcn-vue's own default theme loads a live Google Fonts CDN `@import`** (Geist) — a real network request on every page load, unlike shadcn/ui's Next.js flavor (which uses `next/font`, never a CDN import, so there's no equivalent "harmless if unused" file sitting around). Stripped before appending this pipeline's own font override.
- **create-vuetify's own template download is genuinely flaky**: it fetches its template from GitHub at scaffold time (`giget`-based, not bundled in the npm package) and hit real, repeated 504 Gateway Time-outs during verification — confirmed NOT a real GitHub outage (a plain `curl` against the same URL succeeded immediately every time, including moments after a `create-vuetify` failure). Fixed with a retry loop (4 attempts, escalating 3s/8s/15s backoff) around just that one call — cheap insurance for something entirely outside this pipeline's control.
- **Vuetify's own real installed SCSS already reads `--v-font-body`/`--v-font-heading` CSS custom properties** (confirmed by reading the actual installed package source, since the docs site itself is JS-rendered and unfetchable via a plain fetch) — meaning font wiring needed zero Sass, just a plain stylesheet setting two custom properties. Replaced create-vuetify's own default (`unplugin-fonts` fetching Roboto from `@fontsource`) with this pipeline's own real fetched files.
- **Icons resolved for free**: `@mdi/font` comes vendored by create-vuetify's own default preset, closing the last open "icons as assets" gap from `pipeline-plan.md`'s deferred list (Vuetify was the one library still unresolved there).

**QA note:** verification for this subject was real end-to-end CLI runs (`node src/cli.ts scaffold ...` for all three combinations: plain Tailwind, Tailwind+shadcn-vue, Vuetify), each followed by a real `vue-tsc --build` typecheck and a real `vite build`, with brand colors/fonts confirmed present in the compiled output — same bar as Subject 3's Next.js work, not a lighter one for the second framework.

## Subject 5 — Layer 3: React Native (Expo) scaffolding (NativeWind + React Native Paper)

**Built 2026-09-14, same session as Subject 4.** The user confirmed both paths should be built together, mirroring Vue's structure — a NativeWind base and a separate React Native Paper (MD3) path. See `contracts-and-seeds.md`, "React Native (Expo) scaffold (Layer 3)," for the full written-up contract. This section is the "what broke and how it got fixed" record, same treatment as Subject 4.

**The single biggest finding, discovered before any code got written:** NativeWind v4 (current stable — confirmed via real npm dist-tags: `"latest": "4.2.6"`, v5 only under `rc`/`preview`) has a hard peer dependency on Tailwind CSS **v3**, not v4 — confirmed by inspecting `react-native-css-interop` (NativeWind's own real dependency), whose actual `peerDependencies` pin `"tailwindcss": "~3"`, a much stricter constraint than NativeWind's own loosely-worded `">3.3.0"`. This meant the React Native scaffold could **not** reuse `generate --tailwind`'s output the way Next.js and Vue.js both do — that generator targets Tailwind v4's CSS-native `@theme` syntax. The fix already existed in this pipeline without new work: `generate --rnr`'s output (`rnr/global.css`, built back on 2026-09-10 for RNR's own theming contract) was already written in exactly the right shape — classic `@tailwind base/components/utilities` directives, raw `"H S% L%"` triplets, `.dark:root` selector — because RNR itself needed Tailwind v3 compatibility for the same underlying reason. `--rnr`'s theme became the base for the NativeWind scaffold regardless of whether RNR's own components ever get vendored (they still can't — see the re-verified blocker above).

**`tailwind.config.js`'s color-extend block is copied from RNR's own real upstream template**, not invented — fetched directly from `founded-labs/react-native-reusables-templates`' `minimal` variant on GitHub (the same org whose CLI investigation is written up above), confirmed to use the exact CSS variable names/shapes `generate/rnr.ts` already writes. This pipeline's own success/warning/info/promo status-role extensions were added on top, same treatment `generate/shadcn.ts` already gives them on web.

**Real bugs/gotchas found by actually running the tools, none guessable in advance:**

- **`create-expo-app` handles absolute paths fine** — confirmed by explicit test, unlike create-vue/create-vuetify (Subject 4). No parent-directory workaround needed here.
- **`blank-typescript` (the chosen base template — smallest real option, avoiding `default`/`tabs`' large amount of Expo's own marketing/demo content) has no web support by default.** A real `expo export --platform web` failed outright asking for `react-dom`/`react-native-web` — but RNR's own real upstream template ships both, confirming a real NativeWind (or Paper) project is expected to support web out of the box, not something invented here. Both scaffolds now install them via `expo install`.
- **`create-expo-app --no-install` means `expo install` can't run first** — it needs the `expo` package already in `node_modules` to read the project's SDK version, and errors with "Cannot determine the project's Expo SDK version" if node_modules doesn't exist yet. Fixed with a plain `npm install` (installing the template's own base deps) before any `expo install` call.
- **NativeWind's own `nativewind-env.d.ts` convention doesn't actually declare a `*.css` module** — confirmed by both a real `tsc --noEmit` failure ("Cannot find module or type declarations for side-effect import of './global.css'") and by fetching RNR's own real template's `nativewind-env.d.ts`, which has the exact same gap (just `/// <reference types="nativewind/types" />`, nothing more). `nativewind/types` only adds `className` props to RN components; it was never meant to cover this. Fixed by adding `declare module "*.css";` directly.
- **`inlineRem: 16` is confirmed necessary by RNR's own real template, not just this project's own prior finding** — their `metro.config.js` sets the exact same key to the exact same value, independent confirmation of the `nativewind-project-setup` skill's own fix.
- **RN Paper's icons are resolved for free on Expo** — confirmed against Paper's own real current getting-started guide: "If you use Expo, you don't need to install vector icons — those are part of the expo package." Closes the last open "icons as assets" gap from `pipeline-plan.md`'s deferred list.

**A real, deliberate scope cut, not an oversight: no font files.** Every other scaffold in this pipeline (Next.js, Vue.js) wires real fonts via a plain CSS `@font-face` block pointing at the `.woff2` files `promote --fonts-dir` already fetches. React Native has no CSS and no `@font-face` — real custom fonts need `.ttf`/`.otf` files loaded via `expo-font`'s `useFonts()`, a different file format and loading mechanism this pipeline's font-fetching (built around Google Fonts' CSS2 API, which only serves `.woff2`) doesn't produce. Both React Native scaffolds fall back to the system font, same "degrades gracefully" treatment every other scaffold already uses when `fontsDir` isn't passed — just unconditional here. Extending font-fetching to also grab `.ttf` files is real, separate, not-yet-scoped work.

**QA note:** same bar as Subjects 3–4 — real end-to-end CLI runs for both paths, each followed by a real `tsc --noEmit` typecheck and a real `expo export --platform web` (the closest available equivalent to a real compiled build in an environment with no iOS/Android simulator), with real brand colors confirmed present in the compiled output (the NativeWind path's CSS bundle; the RN Paper path's JS bundle, since Paper applies its MD3-derived theme colors at runtime the same way Vuetify does).

## Subject 6 — Layer 3: Kotlin/Jetpack Compose, resolved as a guide instead of automation

**Decided and built 2026-09-14.** Before any code got written, the user asked which of Kotlin/Android or SwiftUI/iOS to prioritize next. The recommendation was Kotlin, on the reasoning that Gradle offers a real CLI-driveable path where Xcode's own project creation has no non-interactive equivalent at all — that reasoning held up as directionally right, but a closer look found Kotlin's own path has a real gap too, just a different one than SwiftUI's.

**Real research, not assumed — three independent checks, all confirming the same conclusion:**
- **No official `android create <template>` CLI exists.** A first web search surfaced a plausible-sounding `android create empty-activity --name=MyApp` command — re-checked directly against Android's own real, current `developer.android.com/tools` command-line-tools page (which lists every real tool: `sdkmanager`, `avdmanager`, `lint`, `apkanalyzer`, `adb`, build tools, platform tools, the emulator, `jetifier`) and confirmed no project-creation tool exists anywhere in it. The first search result was simply wrong — an old, long-removed `android` tool command from roughly the 2013–2017 era, or a fabrication; either way, not something to build against.
- **`gradle init` is real, but doesn't produce a real Android app.** Verified via an actual local run (installed Gradle 9.7.1 + a real JDK via Homebrew, then `gradle help --task init`): `--type` supports `kotlin-application`, `kotlin-library`, `java-application`, etc. — every one of these is a generic JVM project. No `android-application` type exists. Gradle itself is Android-agnostic; the Android Gradle Plugin (AGP) that turns a Gradle project into a real Android app is a separate Google plugin `gradle init` has no knowledge of.
- **Android Studio itself has no documented headless/batch project-creation mode.** Verified against its own real `developer.android.com/studio/command-line` documentation — every command-line capability documented there is SDK tooling (`sdkmanager`, `avdmanager`, build/platform tools, Gradle itself), never the IDE. File > New > Project's GUI wizard is the only officially documented way to create a new Android project.

**This is a structurally different situation from every other Layer 3 target in this pipeline, not just a harder version of the same problem.** Next.js, Vue.js, and React Native each have a real official non-interactive CLI this pipeline drives directly. Kotlin has none — there is nothing to shell out to, `spawnSync`-style, the way every other scaffold builder in `cli/src/scaffold/` works.

**Decided: a real, filled-in instructions file instead of a `scaffold` command that would have nothing to drive.** This is the same "Pattern A" move already used for Vuetify/React Native Paper's own `SETUP.md` (Subject 2, above) when no automatable install/vendor path exists — just one level up: whole *project creation* instead of "add a library to an existing project." Built as `cli/src/generate/kotlin-scaffold-guide.ts`, called unconditionally whenever `generate --md3` runs (same "always write it, not gated behind `scaffoldMode`" treatment as `SETUP.md`), writing `md3/SCAFFOLD_GUIDE.md` next to `Color.kt`. Real content, not a generic tutorial:
- Real current file locations Android Studio's own "Empty Activity" Compose template creates (`app/src/main/java/<package>/ui/theme/{Color,Theme,Type}.kt`), verified against Google's own current Compose theming documentation.
- **A real, correct simplification worth recording:** the default template's own `Theme.kt` wraps a partial `lightColorScheme(primary = ..., ...)` *builder* call, since its own default `Color.kt` only defines individual color values. This pipeline's own generated `Color.kt` is already a complete `ColorScheme(...)` instance (all 48 real fields — the same shape `generate/md3.ts` has always produced) — so the guide's own `Theme.kt` code is simpler than the template's own default, referencing `LightColorScheme`/`DarkColorScheme` directly rather than re-wrapping them in another builder call.
- **A real, deliberate omission:** the guide's `Theme.kt` skips Android 12+'s "dynamic color" option (`dynamicLightColorScheme(context)`, deriving colors from the device wallpaper) that the default template's own `Theme.kt` usually offers — using it would silently replace this project's real generated brand colors with whatever a given device's wallpaper produces, the opposite of what this pipeline is for. Same "our real values always win over a platform default" principle already applied elsewhere (e.g. avoiding `next/font/google`'s identifier-guessing).
- **A real cross-check, not a coincidence:** the guide references Compose BOM `2026.08.00` (verified current via Android's own BOM-to-library mapping table), which maps to `material3:material3` `1.4.0` — the exact version `generate/md3.ts` has targeted since 2026-09-08, confirmed still correct rather than having silently drifted.
- Conditionally documents the `ElevationOverlay` object only when the user's own shadow tokens are dimension-shaped (same condition `md3.ts` itself already uses to decide whether to emit it) — detected by reading back the already-written `Color.kt` content for the string `"object ElevationOverlay"`, the same "read back what was actually written rather than re-deriving a parallel condition" pattern the Vue/React Native scaffolds already use for their own conditional exports.

**A real bug caught before shipping:** an early draft split a markdown link (`[text]` / `(url)`) and an inline code span across two array-of-lines entries, landing a literal newline between `]` and `(` — which CommonMark does not parse as a link (link text and destination must be adjacent). Caught by actually generating the file and reading the real output, not by inspecting the source array. Fixed by keeping both the link and the code span each on one unbroken line.

**Wired into the `SDSGT-start` skill, not just the CLI:** step 9 (reporting `generate`'s results) now sends `md3/SCAFFOLD_GUIDE.md` explicitly whenever `targetFramework` is `kotlin`, framed as "this is Kotlin's equivalent of step 10," and step 10's own gate no longer lumps Kotlin in with genuinely-unbuilt combinations (Bootstrap-flavored targets, SwiftUI) — it now redirects back to step 9's guide instead of saying "not built yet," since that would undersell what actually happened.

## Subject 7 — Layer 3: SwiftUI/Xcode, resolved as a guide instead of automation

**Decided and built 2026-09-14, same session as Subject 6.** After Kotlin's own resolution, the user asked to check whether SwiftUI had the same kind of automated path Kotlin didn't, and to apply the same guide-instead-of-automation treatment if not.

**Real research, verified on a real Xcode 26.4 install on this machine — not assumed from docs, and stronger verification than Kotlin's own research had available (no Android SDK/emulator exists in this environment; a full macOS + Xcode install does):**
- **No `xcodebuild` project-creation action exists.** Read the tool's own real, complete `-help` usage list — build, test, archive, export, download platforms/components, resolve package dependencies, create xcframeworks, manage localization — nothing that creates a new app project.
- **`swift package init` has no iOS-app template type at all.** Verified via its own real `--help`: `--type` supports `library`/`executable`/`tool`/`build-tool-plugin`/`command-plugin`/`macro`/`empty` — every one is command-line/library-shaped. This is a cleaner "no" than Kotlin's own `gradle init` finding: Gradle's tool at least produced something (the wrong shape, a generic JVM app); Swift Package Manager's `init` doesn't attempt an iOS app shape in any of its options.
- **Xcode's own project templates aren't exposed through any documented CLI hook.** Checked for the template directory location older Xcode versions used to expose — not present at that path in Xcode 26 (reorganized/hidden), and no `xcodebuild`/`xcrun` subcommand references templates at all.

**Same resolution as Kotlin: `generate --swiftui` now always writes a real, filled-in guide instead of a `scaffold` command that would have nothing to drive.** Built as `cli/src/generate/swiftui-scaffold-guide.ts`, writing `swiftui/SCAFFOLD_GUIDE.md` — real current default file locations (`<AppName>App.swift`, `ContentView.swift`), the real "Copy items if needed" + target-membership gotchas when dragging generated files into Xcode's navigator (a real, easy-to-miss mistake, not a generic warning), and real `xcodebuild -showdestinations`/`-destination` commands for building from the command line without hardcoding a specific simulator name that would go stale.

**One real technical problem Kotlin's own guide never had, solved with a second generated file, not just prose:** `generate/swiftui.ts`'s own `DesignTokens.swift` is two flat `enum { static let ... }` namespaces (`Light`/`Dark`) with no built-in way to dynamically switch between them — unlike Compose's `ColorScheme` (switched wholesale by Compose itself) or Vuetify's theme object (switched by `createVuetify()` itself), a plain Swift enum-of-static-lets has no equivalent mechanism. Left as prose, every real call site in the user's app would need a manual `colorScheme == .dark ? DesignTokens.Dark.x : DesignTokens.Light.x` ternary — technically usable, but exactly the "theoretically present, not actually usable" gap this project doesn't leave in place elsewhere. So the guide generator also writes a real `swiftui/Theme.swift` — a standard SwiftUI `EnvironmentKey`/`ViewModifier` pattern, with every one of the project's own real token names wired in, extracted by reading back the already-written `DesignTokens.swift` content (same "read back what was actually written" pattern the Vue.js/React Native/Kotlin guides already use for their own conditional exports) rather than re-deriving the token list from the raw JSON a second time. Branches correctly for a single-mode project too (`Theme.current`, a plain constant — no environment switching to wire up when there's nothing to switch between).

**Verified with the real Swift compiler, not just inspected — the strongest verification any guide-generator in this pipeline has had**, since Xcode happens to be installed on this development machine: `xcrun --sdk iphonesimulator swiftc -target arm64-apple-ios17.0-simulator -typecheck DesignTokens.swift Theme.swift` exits 0 for both the light+dark case and the light-only case, and the guide's own exact usage code sample (a `ContentView`/`@main App` pair using `@Environment(\.theme)` and `.withAppTheme()`) was also compiled for real against the generated files and typechecks cleanly.

**A real bug caught before shipping, same class as Kotlin's own markdown-link bug:** an early draft's "What's in here" section described `Theme.swift` as "the dynamic-switching wrapper" unconditionally, even in the single-mode branch where it's actually a plain constant with no switching at all. Caught by generating both branches for real and reading the actual output, not by inspecting the source template. Fixed to branch the wording the same way the rest of the guide already branches on `hasLight`/`hasDark`.

**Wired into the `SDSGT-start` skill exactly like Kotlin's own guide**, plus one more file: step 9 now sends `swiftui/SCAFFOLD_GUIDE.md` (`display: "render"`) AND `swiftui/Theme.swift` (`display: "attach"`, since it's a source file to drop into Xcode, not something to read inline) whenever `targetFramework` is `swiftui`, framed as SwiftUI's own equivalent of step 10. Step 10's own gate now redirects both Kotlin and SwiftUI back to their step-9 guides instead of the generic "not built yet" line used for genuinely-unbuilt combinations.

**With this, Layer 3 has a real answer — automated scaffold or real guide — for every framework this pipeline supports.** Nothing is left in the "not built" category anymore except specific design-language combinations within already-supported frameworks (Bootstrap on Next.js/Vue.js/React Native, none of which have ever had a component-library story either).
